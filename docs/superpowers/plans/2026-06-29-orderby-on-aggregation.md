# ORDER BY on a Faceted Aggregation — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every `ORDER BY` the translator emits onto an aggregation either faithful or loud — drop it when it is redundant, restructure it into a subquery when a faithful form exists, and emit `unsupported` only when no faithful NRDB form exists.

**Architecture:** NRDB honors `ORDER BY` only on a **non-aggregating** result; on an aggregation it is ignored and the rows are ranked by the first aggregate descending (`.claude/references/nrql-reference.md`; engine `../dirac/dirac-nrql`). The handlers already set `ir.orderBy` to the SPL author's *intent* (`top`→count DESC, `rare`→count ASC, `sort`→field+dir, `tail`/`reverse`→timestamp). So instead of scattering decisions across handlers, add **one late optimizer pass** (`orderByOnAggregationPass`) that runs after the post-aggregation fold, detects an `ORDER BY` landing on an aggregation, and applies the three outcomes uniformly: **drop** (redundant), **subquery-restructure** (faithful), **unsupported** (no faithful form). Handlers change only where intent is otherwise unrecoverable from `(field, dir, shape)` — `tail` and `reverse` get a small `_orderByKind` marker.

**Tech Stack:** Pure ESM JS; IR node factories in `src/ir/nodes.js`; optimizer passes in `src/ir/optimize.js`; reusable subquery helpers in `src/ir/foldPostAggregation.js` and `src/input/spl/splExprUtils.js`; message catalog in `src/messages.js`; Vitest data-driven `cases`. No grammar change.

**Source spec:** `docs/superpowers/specs/2026-06-29-orderby-on-aggregation-design.md`.

**Branch strategy:** `feat/orderby-on-aggregation` off `origin/master`; Tasks 2–4 stack on it (or land as one branch with four commits). **This supersedes PR #95** (`feat/render-fails-order-by`): the pass-based approach subsumes #95's handler-level `ORDER BY` drops — the pass drops `handleTop`'s redundant clause without editing `handleTop`. When this opens, close PR #95. (Confirm close-vs-stack with the human before opening.)

## Engine-Grounded Facts (load-bearing — do not re-derive)

Verified against staging (acct 1, 2026-06-29) + `dirac-nrql` + `.claude/references/nrql-reference.md`.

- `OrderBy(field, descending)` → `{type:'OrderBy', field, descending}`. `descending: true` = DESC, `false` = ASC. The emitter renders `ORDER BY <field> <DESC|ASC>` (`irToNrql.js:291`).
- **`ORDER BY` is honored only on a non-aggregating result.** On a faceted aggregation it is ignored and rows are ranked **by the first aggregate, descending**; `LIMIT` then truncates that ranking (FACET defaults to `LIMIT 10`). A row-wise outer over a subquery (`SELECT host, count AS pct`) is non-aggregating → `ORDER BY` honored.
- **Faithful form:** `FROM (FROM Log SELECT <aggs> FACET <keys> LIMIT MAX) SELECT <keys>, <aggExposedNames> ORDER BY <sortKey> <dir> LIMIT N`. The outer is a non-aggregating projection; it does the ordering and the top/bottom-N selection.
- **Subquery result cap = 5000 rows regardless of `LIMIT MAX`** (the *subquery result cap*, not `LIMIT MAX`). Faithful for ≤5000 distinct group-key values; above that, any order other than first-aggregate-DESC keeps the wrong 5000 → warn.
- **Subquery-exposed column names** (`exposedNameOf`): an `Alias` exposes its alias name; a bare `Function` exposes its NRQL name (`count`→`count`, `average`, `sum`, `min`, `max`, `latest`, `earliest`, `uniqueCount`), except `stddev`→`standarddeviation`. `median`/`percentile`/`uniques` expose keyed objects/lists — **out of scope here** (sorting by one is not in the corpus; if a sort key resolves to one, the not-in-result guard below makes it `unsupported`).
- **`wrapAsSubquery(ir)`** (`splExprUtils.js:289`) moves `select/facet/where/bindings` and `timeseries` into a new inner `SelectQuery`, sets the inner `LIMIT MAX` when faceted, and clears those on the outer. It does **not** touch `ir.orderBy` or `ir.limit` — the outer keeps both.
- `transformTree` does **not** descend into `SubquerySource` (`transform.js:7`), so this top-level pass never rewrites inner subqueries.

```js
/**
 * ORDER BY on an aggregation.
 *
 * NRDB honors ORDER BY only on a non-aggregating result; on an aggregation it is
 * ignored (rows are ranked by the first aggregate, descending) and the dashboard
 * widget engine rejects it. This late pass — registered AFTER the post-aggregation
 * fold — detects an ORDER BY landing on an aggregation and either drops the
 * redundant implicit order or marks it unsupported. (Subquery-restructure for the
 * faithful-but-non-redundant orders is added in a follow-up.)
 */
import { isAggregateExpr, exposedNameOf } from './foldPostAggregation.js';
import { messages } from '../messages.js';

// ORDER BY lands on an aggregation when the top-level result groups (FACET) or
// selects an aggregate. A row-wise outer over a subquery (SELECT host, count AS
// pct, or SELECT * WHERE …) has neither, so ORDER BY is honored there → false.
function landsOnAggregation(ir) {
  if (ir.facet.length > 0) return true;
  return ir.select.some(isAggregateExpr);
}

// Exposed name of the first aggregate in the query's own SELECT (count → 'count',
// avg(x) as a → 'a', …); null when there is none.
function firstAggregateName(ir) {
  const agg = ir.select.find(isAggregateExpr);
  return agg ? exposedNameOf(agg) : null;
}

// True when ORDER BY is exactly the implicit faceted ranking — DESC by the first
// aggregate — which NRDB already returns, so the clause is redundant.
function isImplicitFacetOrder(ir) {
  if (!ir.orderBy?.descending) return false;
  const f = ir.orderBy.field;
  return f?.type === 'Identifier' && f.name === firstAggregateName(ir);
}

export function orderByOnAggregationPass(ir) {
  // Skip queries already failed elsewhere (a prior pass / handler pushed
  // unsupported) — never pile a second diagnosis on the same query.
  if (!ir.orderBy || ir.unsupported.length > 0 || !landsOnAggregation(ir)) {
    return ir;
  }

  // tail/reverse after an aggregation: SPL slices/flips a stats-specific row order
  // NRDB does not define. No faithful form → loud unsupported.
  if (ir._orderByKind === 'tail') {
    ir.unsupported.push(messages.order_tail_after_aggregation());
    return ir;
  }
  if (ir._orderByKind === 'reverse') {
    ir.unsupported.push(messages.order_reverse_after_aggregation());
    return ir;
  }

  // Non-faceted single-row aggregation (stats count): nothing to order. Drop the
  // no-op — left in place, SELECT count(*) ORDER BY count DESC is widget-rejected.
  if (ir.facet.length === 0) {
    ir.orderBy = null;
    return ir;
  }

  // Faceted aggregation: drop the redundant implicit order; anything else is not
  // faithfully expressible yet → unsupported (the follow-up restructures it).
  if (isImplicitFacetOrder(ir)) {
    ir.orderBy = null;
    return ir;
  }
  ir.unsupported.push(
    messages.order_on_aggregation_unsupported(
      ir.orderBy.field?.name ?? 'the requested field',
    ),
  );
  return ir;
}
```

// Wrap the flat faceted aggregation in a subquery and order on the (row-wise) outer,
// which NRDB honors. The outer projects the inner's exposed columns; ORDER BY then
// selects the real top/bottom-N. Faithful up to the 5000-row subquery cap.
function restructureForOrderBy(ir) {
  // Inner aggregates expose bare names (count, average, …); a collision silently
  // keeps the last, so a sort key could read the wrong column. Fail loud.
  const collision = duplicateExposedName(ir);
  if (collision) {
    ir.unsupported.push(messages.subquery_name_collision(collision));
    return ir;
  }
  const aggregates = ir.select.filter(isAggregateExpr);
  const facetKeys = ir.facet.map((f) => Identifier(f.name));
  const aggCols = aggregates.map((a) => Identifier(exposedNameOf(a)));
  // Only facet keys and SCALAR aggregates can be ordered; median/percentile/uniques
  // expose keyed objects/lists (ordering by one is silently wrong → unsupported).
  const sortable = new Set([
    ...facetKeys.map((f) => f.name),
    ...aggregates.filter((a) => extractNonScalar(a) == null).map(exposedNameOf),
  ]);
  const sortKey =
    ir.orderBy.field?.type === 'Identifier' ? ir.orderBy.field.name : null;
  if (!sortKey || !sortable.has(sortKey)) {
    ir.unsupported.push(
      messages.order_on_aggregation_unsupported(sortKey ?? 'the requested expression'),
    );
    return ir;
  }
  wrapAsSubquery(ir); // select/facet/where → inner (LIMIT MAX); outer keeps orderBy + limit
  ir.select = [...facetKeys, ...aggCols];
  // The inner now carries LIMIT MAX, so the build-time FACET-defaults-to-10 warning
  // no longer applies (the outer is not faceted). Drop it; the cap warning replaces it.
  ir.warnings = ir.warnings.filter((w) => w !== messages.facet_default_limit());
  ir.warnings.push(messages.subquery_facet_cap(facetKeys.map((f) => f.name).join(', ')));
  return ir;
